```typescript
export const APP_VERSION = '1.0.0';

export function checkVersionChange(): boolean {
  const stored = localStorage.getItem('app_version');
  if (stored !== APP_VERSION) {
    // Clear all caches on version change
    if ('caches' in window) {
      caches.keys().then(names => {
        names.forEach(name => caches.delete(name));
      });
    }
    localStorage.setItem('app_version', APP_VERSION);
    return true;
  }
  return false;
}

export function getAppVersion(): string {
  return APP_VERSION;
}

export function getBuildDate(): string {
  return __BUILD_DATE__;  // Injected at build time
}

export function logVersionInfo(): void {
  console.log(`
┌─────────────────────────────────────────┐
│ 🎮 Colombia Departments Puzzle v${APP_VERSION}   │
│ 🏗️  Built: ${new Date(__BUILD_DATE__).toISOString().split('T')[0]}                  │
└─────────────────────────────────────────┘
  `);
}
```

## Technical Decisions

### Decision 1: Multi-Layer Cache Control Strategy

**Context**: Need reliable cache control across all browsers and CDNs

**Options Considered**:
1. **HTTP Headers Only** - Pros: Server-side control Cons: May be ignored by proxies
2. **Meta Tags Only** - Pros: Always sent to browser Cons: No CDN control
3. **Multi-Layer Approach** - Pros: Redundancy, works everywhere Cons: More complex

**Decision**: Multi-layer approach (HTTP headers + meta tags + SW updates)

**Rationale**:
- HTTP headers control CDN and proxy caching
- Meta tags ensure browser compliance even if headers stripped
- SW updateViaCache ensures service worker always checks
- Redundancy prevents any single point of failure

**Trade-offs**: More configuration overhead, but bulletproof reliability

---

### Decision 2: Version-Based Cache Invalidation

**Context**: Need automatic cache clearing when app updates

**Options Considered**:
1. **Manual Invalidation** - Pros: Simple Cons: Users forget, error-prone
2. **Build Hash** - Pros: Automatic Cons: Complex to implement
3. **Semantic Version** - Pros: Clear, simple Cons: Manual increment needed

**Decision**: Semantic versioning with automatic cache clearing

**Rationale**:
- `APP_VERSION` constant easy to update
- `checkVersionChange()` runs on every app mount
- Automatic cache clearing via CacheStorage API
- Version visible in console for debugging
- Clear upgrade path (1.0.0 → 1.0.1 → etc.)

**Trade-offs**: Requires manual version increment, but simple and reliable

---

### Decision 3: Build Timestamp Injection

**Context**: Need to identify which build is running in production

**Options Considered**:
1. **Git Commit Hash** - Pros: Unique Cons: Requires git, not semantic
2. **Build Timestamp** - Pros: Human-readable Cons: Not unique across builds
3. **Both** - Pros: Best of both Cons: Overkill

**Decision**: Build timestamp injected via Vite define

**Rationale**:
- ISO 8601 timestamp human-readable
- Vite define makes it available everywhere
- Helps debugging "which version is deployed?"
- Combines well with semantic version
- No external dependencies (no git required)

**Trade-offs**: Not globally unique, but sufficient for debugging

---

### Decision 4: Vercel Cache Duration Settings

**Context**: Balance between performance (caching) and freshness (updates)

**Decision**:
- `index.html`: 0 seconds (always fresh)
- `sw.js`: 0 seconds (always fresh)
- `manifest.json`: 1 hour (reduced from 24h)
- `assets/*`: 1 year immutable (content-hash)

**Rationale**:
- HTML and SW must always be fresh (entry points)
- Manifest can cache briefly (1h vs 24h is 96% faster updates)
- Assets with content-hash can cache forever (URL changes when content changes)
- Follows industry best practices (Google, Facebook, etc.)

**Trade-offs**: More frequent manifest fetches, but enables faster PWA updates
